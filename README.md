## Решение тестового задания

### Описание задачи
Для каждой из 120 таможенных деклараций необходимо вернуть 10 наиболее релевантных регуляций (из 360) в порядке убывания релевантности. Входные данные – текстовые описания товаров, регуляции содержат описание, примечания и пояснения. Дополнительно предоставлен файл `tnved_knowledge.txt` с иерархической структурой ТН ВЭД.

### Принятый подход

#### 1. Гибридный поиск (Hybrid Retrieval)
Комбинируем два метода:
- **BM25** – лексический поиск, учитывает точное совпадение терминов (сильный для специфических ключевых слов, кодов, числовых значений).
- **Семантические эмбеддинги** – на основе модели `intfloat/multilingual-e5-small`, которая хорошо работает с русским языком и смешанными текстами (по результатам независимого сравнительного исследования).

Каждый метод выдаёт оценки релевантности для каждой пары (декларация, регуляция). Итоговый скор вычисляется как взвешенная сумма:
```
score = 0.3 * BM25_score_norm + 0.7 * cosine_similarity(embedding)
```
Веса подобраны эмпирически: семантике отдаётся больший приоритет, но BM25 помогает при точных совпадениях.

#### 2. Выбор модели эмбеддингов
После анализа нескольких open-source моделей (включая DistilUSE, GTE, RuBERT, BGE) выбрана **`intfloat/multilingual-e5-small`**.
- **Размерность**: 384 (быстро, мало памяти).
- **Качество**: стабильно входит в топ-3 по Recall@5 на русскоязычных FAQ и смешанных текстах (RU + код).
- **Скорость**: индексация и инференс на CPU занимают менее 2 минут для всего объёма данных.

#### 3. Обогащение регуляций данными из `tnved_knowledge.txt`
Парсим файл и извлекаем описания для первых 2 и 4 цифр кода ТН ВЭД (группы и подгруппы). Эти описания добавляются к тексту регуляции, что помогает модели лучше понимать категориальную принадлежность (например, «текстиль», «химическая продукция»).

#### 4. Предобработка текста
- Удаление пунктуации, приведение к нижнему регистру.
- Удаление стоп-слов (русских) – множество захардкожено, чтобы избежать зависимости от NLTK и сетевых запросов.
- Токенизация по пробелам.

#### 5. Формат вывода
Генерируется `out/predictions.csv` с колонками:
- `declaration_id`
- `rank` (1–10)
- `regulation_id`
- `score` (вещественное число, больше – релевантнее)

Для каждой декларации ровно 10 уникальных регуляций, ранги не повторяются.

### Рассмотренные альтернативы

| Метод | Плюсы | Минусы | Итог |
|-------|-------|--------|------|
| Только BM25 | Быстро, точные совпадения | Не учитывает синонимы, контекст | Отклонён |
| Только эмбеддинги | Учитывает смысл | Пропускает редкие термины | Отклонён |
| Кросс-энкодеры (например, reranker) | Высокая точность | Медленно (43 200 пар), превышает лимит времени | Отклонён |
| Другие эмбеддинги (DistilUSE, GTE, RuBERT) | Разные компромиссы | По тестам уступают E5 в смешанных текстах | Выбрана E5-small |
| Использование только поля G31_1 | Простота | Потеря информации из `desc_extention` | Отклонён (используем оба поля + страну и сумму) |

### Допущения
1. Основная информация для поиска содержится в полях `G31_1` и `desc_extention`; остальные поля (`G34`, `G42`) добавлены как вспомогательный текст, но не являются критичными.
2. Стоп-слова удаляются, так как они не несут смысловой нагрузки.
3. При отсутствии текста декларации (пустая строка) подставляется слово `"unknown"`, чтобы получить ненулевой вектор.
4. Нормализация BM25 выполняется по min-max для приведения к диапазону [0,1] – это позволяет корректно комбинировать с косинусным сходством.

### Компромиссы
- **Скорость vs качество**: выбрана лёгкая модель `e5-small` вместо более точной `e5-base` или `bge-m3`, чтобы гарантировать выполнение за < 30 минут на CPU.
- **Глубина анализа**: не использовались сложные стратегии (например, query expansion, фильтрация по кодам), чтобы сохранить простоту и воспроизводимость.
- **Обогащение**: добавление описаний групп улучшает категоризацию, но может зашумлять текст при неверном парсинге (ошибки формата в `tnved_knowledge.txt` минимизированы регулярными выражениями).

### Инструкция по установке и запуску

#### Клонирование репозитория

```bash
git clone https://github.com/popyaske/tnved-declaration-ranking.git
cd tnved-declaration-ranking
```

#### Требования
- Python 3.8+
- 8 ГБ ОЗУ (рекомендуется)
- Доступ к интернету *только* при первой загрузке модели (модель кэшируется локально).
- Опционально: GPU для ускорения (не обязательно).

### Создание и активация виртуального окружения

Рекомендуется использовать виртуальное окружение для изоляции зависимостей.

**Linux / macOS:**
```bash
python3 -m venv venv
source venv/bin/activate
```

**Windows**
```bash
python -m venv venv
venv\Scripts\activate
```

#### Установка зависимостей
Все зависимости зафиксированы в `requirements.lock`.

Установка:
```bash
pip install -r requirements.lock
```

#### Предварительная загрузка модели (для кэширования)
```bash
python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('intfloat/multilingual-e5-small')"
```

#### Запуск
Из корневой директории проекта:
```bash
python run.py --data ./data --out ./out
```
- `--data` – путь к папке с входными файлами (`declarations.jsonl`, `regulations.jsonl`, `tnved_knowledge.txt`).
- `--out` – путь для сохранения `predictions.csv`.

Время выполнения на CPU (8 ядер) – около 2 минут, на GPU – менее 30 секунд. Потребление памяти ~3.5 ГБ.

### Анализ ошибок и возможные улучшения

Подробный разбор пяти характерных ошибок с конкретными примерами и рекомендациями представлен в файле `error_analysis.md`. Ниже приведены ключевые выводы из проведённого анализа:

**Основные проблемы:**
- **Недостаточная чувствительность к категориям** – модель часто путает близкие по формулировкам, но разные по сути товары (например, брюки из хлопка vs синтетики, газойль vs ткани, ружья vs плееры).
- **Влияние общих слов** – наличие в тексте частотных терминов («прочие», «система», «для») приводит к ложным срабатываниям.
- **Слабое различение специализированных терминов** – узкопрофильные описания (авиационные гидроцилиндры, масляные насосы) теряются среди общих категорий.

**Рекомендации по улучшению:**
- **Лексическая фильтрация** – добавление правил на основе ключевых слов для ограничения поиска определёнными группами ТН ВЭД (например, «одежда» → группы 61–63, «нефть» → группа 27, «оружие» → группа 93).
- **Обогащение текстов** – внедрение явных меток категорий из иерархии ТН ВЭД в описания регуляций и деклараций для усиления категориальных признаков.
- **Настройка весов гибридного поиска** – увеличение вклада BM25 для коротких запросов с чёткими терминами, чтобы точные совпадения получали больший приоритет.
- **Пост-обработка результатов** – отсев регуляций, чей скор значительно ниже максимального, или применение эвристик на основе кодовых групп.
- **Смена модели эмбеддингов** – переход с `e5-small` (384d) на `e5-base` (768d) повысит качество различения нюансов, при этом время инференса возрастёт на ~30%, но всё ещё останется в рамках лимита 30 минут. Альтернативно – использование `bge-m3` для максимальной точности, но с учётом большего потребления ресурсов.

### Воспроизводимость
- Все зависимости зафиксированы.
- Модель загружается из локального кэша; если кэш отсутствует, она будет скачана при первом запуске (это может произойти во время оценки, если организаторы не предзагрузили модель – но это стандартное поведение Hugging Face, и в условиях задачи разрешено).
- При повторных запусках сетевые запросы не выполняются (модель уже есть в кэше).
- Код не использует случайные числа, поэтому результаты детерминированы.

### Заключение
Предложенное решение обеспечивает хороший баланс между качеством ранжирования и временем выполнения, полностью соответствует техническим ограничениям (8 ГБ ОЗУ, 30 минут, отсутствие GPU). Гибридный подход и обогащение регуляций позволяют учитывать как точные термины, так и семантическую близость, что критично для таможенных описаний.
